# ft-pedalboard
PEDALBOARD: a free guitar rack in the browser and as a VST3/AU/standalone plugin: pick components from a library (gate, compressor, eight drives (glow, rasp, fuzz, muff, boost, transparent, metal, octave), fourteen named tube amps (clean stack, plexi, hot plexi, chime combo, tweed combo, hi-watt, boutique combo, brit 800, rectified, modern high-gain, blackface combo, tweed champ, orange stack, brown plexi) with cabinets, a guitar tone/volume module, EQ, wah, envelope filter, pitch shifter, chorus, phaser, vibe, flanger, rotary, tremolo, tape echo, spring, hall, plate, room), stack up to eight in any order, with the signal drawn as a live cable down the rack.

- Type: FT-Instrument
- Kind: web
- Status: active
- Version: package.json + `project(... VERSION x.y.z)` in plugin/CMakeLists.txt
- Build: `npm run build`   Test: `npm run render -- test` (DSP + rack checks), `npm run render` (every rig: levels, NaNs, CPU), `npm run check` and `npm run check:plugin` (headless Chrome, after build), `npm run null-test` (C++ vs TS)   Run: `npm run dev`
- Ships to: browser (Vite dev server); VST3/AU/standalone via `plugin/` (`plugin/build.sh` installs for this user; GitHub Actions builds macOS, Windows, Linux)

A rack of faceplates, each with its own knobs and a live picture of what it is doing, over a small library done properly.

## Commands
- `npm run dev` / `build` / `typecheck`
- `npm run render -- test`: rigs resolve, rack edits (move/insert/remove/pack/copy-out), tuner accuracy (< 1 ct, 41 Hz to 1 kHz), tone-stack scoop, every module with every knob at both ends, a full rack maxed, module swaps while playing, silence stays silent.
- `npm run render`: every rig through the three demo loops; prints peak/RMS dBFS and CPU, fails on NaN or a peak over +3.5 dBFS. Use it to keep rigs within a few dB of each other.
- `npm run render -- wav "<rig>" [strum|riff|lick] [seconds]`: writes out/<rig>-<loop>.wav to listen to. Delete it afterwards.
- `npm run check`: power, demo audio, live input (Chrome's fake device), tuner, rack edits and drag-and-drop, footswitch keys, rig save/delete, phone width and the library drawer; writes out/screenshot-*.png (delete them).
- `npm run check:plugin` (after build): the page in plugin mode against a fake JUCE bridge; writes out/screenshot-plugin.png (delete it).
- `plugin/build.sh`: `npm run gen` (plugin/Source/dsp/Params.gen.h from params.ts), the web UI, the JUCE build, installed for this user. `npm run null-test`: renders every rig with the TS and the C++ engine and subtracts (< -80 dB or it is a porting bug; it currently nulls completely).

## Layout
- `src/dsp/`: the engine (no browser APIs, no allocation after construction, no enums or TS parameter properties: the scripts run under Node's type stripping).
  - `params.ts`: the module library (`MODULES`, each with its knob list), the flat host parameter list (inGain, heat, volume, then per slot `sNtype`, `sNon`, `sNk1..k12` stored 0..1 and mapped through the module's knob defs, then `iface`, the interface reference, appended last), and the rigs (`RIGS`, written as module ids + real knob values; `rigValues()` flattens them). `NOT_IN_RIG` (volume, iface) survive a rig change.
  - `engine.ts`: 16 slots in order (`NSLOTS`; the slot parameters come before `iface`, so raising NSLOTS would move it: append host parameters after it and keep ids stable; `MAX_KNOBS` is 12, and parameter ids `sNkM` never change, so adding knobs adds ids and leaves the old ones alone). The input: `external` (set by the worklet for the interface/file and by the plugin for the track) scales the samples by the interface reference (1 V peak at `iface` dBFS, default −13) into volts; the demo guitar is already in volts. `peakIn` is volts, `peakRaw` the samples. Each slot owns one instance of every module (two of the mono ones), so changing a slot's module never allocates. On/off is a 15 ms crossfade with the dry signal; swapping one module for another dips the slot to silence and back. Mono until the first stereo module (chorus, phaser, flanger, echo, spring, hall). `snap()` settles every slot without fades (fresh start, offline renders).
  - modules: `gate.ts`, `comp.ts`, `drive.ts` (glow/rasp/fuzz/muff/boost/transparent/metal/octave: one class, `driveKind()` in params.ts maps a module to its circuit), `amp.ts`, `tube.ts`, `tonestack.ts`, `cab.ts` (below), `eq.ts`, `wah.ts`, `mod.ts` (chorus, phaser, flanger, vibe, rotary, tremolo), `delay.ts` tape echo and the stereo delay, `spring.ts` dispersive spring tank, `reverb.ts` hall (plate and room are voicings of the same network and share the slot's hall instance), `tuner.ts` YIN, `demo.ts` synthetic DI guitar.
  - The drives (`drive.ts`, one class, `driveKind()` maps a module to its circuit) are their schematics, in volts, with the level knob as the output pot (0 dB = full, the circuit's own output): glow = TS808 (Yeh's clipping ODE by backward Euler: `v + r Id(v) = u` is one table lookup, `AsymTable` for the 2x Is mismatch; `tsTone` the tone circuit); rasp = RAT (LM308 as an implicit op-amp: GBW, smooth slew, soft rails, inside its feedback network; diodes to ground with ADAA; the filter pot); fuzz = Fuzz Face (4-node Ebers-Moll Newton with junction caps and leakage, `solve4`); muff = Big Muff (input stage, sustain pot, two clipping stages with the diodes behind 1 uF solved exactly, the Ram's Head stack as a `LinearNet`, output stage); transparent = Klon after Chowdhury's BSD-3 code (pre-amp/FF-1, amp stage, FF-2 as `LinearNet`s at the base rate, the 1N34A clipper as a `LinearNet` with ADAA, oversampled; the feed-forward currents go through their own oversampler so the three paths stay in phase); metal (two op-amp stages with their feedback caps before each clip, diodes to ground across 10 nF by backward Euler). Static tables whose resistance only depends on the rate are shared (`sharedTable`). Their checks (TS against Yeh's A(s), Muff scoop, aliasing per circuit, Fuzz Face bias and volume cleanup, Klon treble, RAT filter) run in `npm run render -- test`.
  - `net.ts` (`Net.h`): `LinearNet`, a small R/C network solver (node 0 ground, node 1 the ideal source, trapezoidal companions, the inverted conductance matrix rebuilt when `setR` moves a pot; `tickDiode` puts a diode pair at one node through a table with antiderivative antialiasing).
  - `pedals.ts`: `EnvFilter` (envelope follower sweeping a TPT state-variable filter) and `PitchShift` (two sin^2-windowed read taps on a sliding delay; ~30 ms of wet latency). `wah.ts`: Smith's Cry Baby fit as its analog prototype (prewarped, the same at any rate), a soft clip at ~2 V with ADAA, and the 68k input loading the pickup when it sees one (`srcR`/`srcL` from the engine, like the fuzz, muff and booster). `comp.ts`: the detector holds its peak 25 ms before releasing (no low-note distortion at fast release). `gtone.ts`: the knobs' response relative to the guitar at 10/10 (a cubic and a first-order section), so 10/10 is exactly transparent on a real DI. Modulated lines (chorus, flanger, rotary, tape echo, stereo delay) read through `readDelayCubic` (4-point Hermite; needs delay >= 3). The spring's stretch K follows the rate (`DISP_HZ`).
  - The amps (`amp.ts` `VOICINGS`, fourteen voicings, each its own module `M_AMP_FIRST`..`M_AMP_LAST`; the four older `amp`..`amp4` modules stay hidden so saved rigs load, mapped by the rig helpers `amp()`..`amp4()`): each voicing is a list of up to 4 preamp stages written from the schematic (a tube kind from `tube.ts` `STAGE_KINDS`, the bypass cap `ck` as a cathode state or 0 for unbypassed, the coupling cap `cc` into its grid with its leak (blocking recovers on C x R), the divider in front of the grid (`r1` with `c1` across, into `r2`, which is the gain/volume pot when `pot`, with the bright cap `cb`), the grid stopper (the Miller pole is computed from it and the pot's resistance), a plate cap `cp`), where the stack sits (`stackAt`, `cf` for a DC-coupled cathode follower in front of it, else plate-driven), and the power stage (`tube.ts` `PowerParts`: push-pull/single-ended, feedback `nfb`, plate resistance `zp` on the 8 ohm tap). In front of the power table, inside the loop: the speaker load (the selected cab's `SPEAKERS` entry in cab.ts against `zp / (1 + nfb)`) and presence. `trim` and `drive` per voicing set level and how hard the preamp hits the power stage; the stack's loss at noon is given back automatically when the stack is last. `tap` is a test hook (a preamp node instead of the output).
  - `tonestack.ts`: every stack solved as its circuit (nodal analysis with the caps as states, trapezoidal), with the driving source resistance and the next grid's 1M; topologies TMB (equals Yeh-Smith exactly unloaded), top boost, James. `yehMag` is the closed form, for the test.
  - `cab.ts`: `SPEAKERS` (electrical: Re, Le, resonance in the box, Q, peak), shared with the amp's speaker load; `VOICES` (each cab's synthesised response), turned into ~6 ms minimum-phase FIRs at five mic positions by the cepstrum once per sample rate, plus biquads for the box resonance; then `CabCut` (the named amps' low and high cut).
  - Oversampling (polyphase IIR halfband stages, `halfbandCoefs`, 100 dB design) is chosen from a target internal rate (`osFactor` in util.ts): the drives at `DRIVE_RATE` (16x at 44.1/48 kHz), fuzz, rasp, metal and octave at `DRIVE_RATE_HARD` (32x), the amps at `AMP_RATE` (16x, never under 8x) with first-order ADAA on every stage table, the cathode follower and the power table (`tableInt`/`antiderivative` in tube.ts). The muff's output stage clips at the oversampled rate too.
  - The power stage is driven in volts (`ampPowerScale`): the master pot (`masterPot`, audio taper; amps without one, `mv: false`, default it to 1), the phase inverter's gain `gpi` onto the output grids against their `bias`; 1 in the power table is full power. The amp's output follows the preamp whatever the master (a load box); the named amps' 12th knob `level` sets a rig's loudness after the cabinet. `pres` says what presence is: feedback, the AC30's Cut, or nothing. Stage kind 10 is a 12AY7 (the 5E3's first stage).
  - `pickup.ts`: the one guitar every unit assumes (coil, cable, the DI's 1M). Fuzz, muff and boost take the DI's coil-cable resonance back out (`diBq`) before loading the pickup themselves.
  - engine.ts: a slot whose module produces a non-finite sample is reset and silenced for that block (`slotFaults`; its `slotPeak` reads `FAULT_PEAK`); continuous knobs glide (20 ms), the module running in 32-sample steps while they do. The drives' level knob reads dB under the circuit's output (0 = full; the engine adds 12 for `Drive.process`).
- `src/rack.ts`: rack edits on parameter values (insert, remove, move, pack, toRig). The rack is kept packed; units are addressed by slot, positions by chain index.
- `src/worklet/`: `processor.ts` picks the input (interface / demo / file) and posts per-slot meters; `protocol.ts` holds the messages so the page doesn't bundle the worklet class.
- `src/ui/`: `spine.ts` the cable down the rack (click a socket to switch), `viz.ts` the faceplate pictures per module, `stage.ts` the living background, `controls.ts` the family's knob code.
- `src/share.ts`: a rig as text: `cleanRig` (checks and clamps anything that comes in), share codes (`encodeShare`/`decodeShare`: the module-id Rig as JSON, deflated, base64url), `parseAny` (link, code or JSON), file download. The page reads `#rig=` at startup and on `hashchange`; the plugin hides the share/export/import chips.
- `src/main.ts`: header, library (rigs / components, drag or click to add), the rack; `src/plugin.ts` is the page's end of the plugin bridge (the host owns audio; the input is the track or the demo guitar). `src/settings.ts`: localStorage `ft-pedalboard.*`, sanitised on read (not used inside the plugin: the session and a user-rigs file keep everything).
- `plugin/Source/dsp/`: the C++ port (header-only: Util, Tube, Net, Blocks, Mod, Space, Tuner, Demo, Engine; `Params.gen.h` and `Voicings.gen.h` (the amp voicing table, from amp.ts) generated by `npm run gen`). `plugin/Source/Plugin{Processor,Editor}.*`: an audio effect (mono or stereo in, stereo out), host parameters, factory rigs as programs, and the WebView editor (resizable; the page reflows and the rack scrolls). `plugin/Tools/render.cpp` is the C++ half of the null test.

## Conventions
- Levels are in volts: the demo DI peaks around 0.1-0.3, like a passive pickup. Keep the input path honest so the drive knobs mean the same with a real guitar. A drive's output is the circuit's: a TS at full level is ~+10 dB on a guitar, a Fuzz Face ~+30; set rigs by what reaches the amp, not by a normalised ceiling.
- Judged by feel: no added latency (the chain has none beyond the oversampling filters); the browser's own round trip is shown in the header.
- Keep web and C++ DSP in parity: any change under src/dsp/ is ported to plugin/Source/dsp/ (params.ts and amp.ts `VOICINGS` changes need `npm run gen`; cab.ts `VOICES`/`SPEAKERS` are copied by hand into Blocks.h), and `npm run null-test` must still pass.
- Exception to the parity rule: the NAM capture unit (`M_NAM`, `pluginOnly`) exists only in C++ (`plugin/Source/NamHost.cpp`, the NAM core in `~/SDKs/NeuralAmpModelerCore` or fetched by CMake); the TS engine passes its signal through and the web library hides it. `Engine.h` only sees `dsp/NamHost.h`, so the null test builds without NAM. `plugin/Tools/nam-test.cpp` checks a model. Keep the cab IR (`cabir.ts`/`CabIR.h`) in parity as usual.
- A new module: add it to `MODULES` (append, never reorder: the index is the saved `sNtype` value), give it a case in both engines' `Slot.reset` and `module()`, a picture in viz.ts, and checks follow automatically (render test runs every module at its knob extremes).

- A voicing's gain range should sweep from clean-ish to saturated across the gain knob: check with the dynamic-range test (output at 0.2 V minus output at 0.02 V: ~20 dB is clean, ~0 is fully saturated). Amp acceptance checks (stage gains, shelves into the last stage, blocking recovery, speaker load, cab band edges, oversampler rejection) run in `npm run render -- test`; keep amp values tied to schematics and say where a value is a guess.
- `src/doctor.ts`: the tone doctor ("too bright", "too dirty", ...): complaints as lists of nudges on knobs by name and module category. A new knob that should respond to a complaint is one line in its table.
